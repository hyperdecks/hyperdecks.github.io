gRPC: RPC for the 2020s

gRPC uses Protocol Buffers as IDL

-Cross-platform library for serializing structured data

-Payload is serialized into non-ASCII binary (supported by strong typing)

-Permits auto-generation of clients for many languages

gRPC and protobuf aren’t the only modern RPC Framework and IDL

-Apache Thrift [> Facebook, now open-source]: Thrift Definitions, a lot of choice in the stack

-Bond [> Microsoft]: Focuses on richer IDL (e.g., supports inheritance)

-Apache Avro [> Hadoop]: JSON Schema for IDLs; not as extreme as protobuf

gRPC then makes use of HTTP/2 as transport (not: application!) protocol

IntellIoT enables flexible and individualized production—a crucial feature for the manufacturing plant of the future. Thinking even further, shared manufacturing plants with multiple customers utilizing manufacturing as-a-service will be possible.

On the Web, contracts are composed of protocols that refer to media types

Hyperlinks are provided by servers to inform clients about their options.

HTTP constructs (methods, headers, status codes) specify how to interact with a resource.

Media types help clients understand what they can expect at the end of a hyperlink.

Link relations capture why a client would want to follow a link given an agreed-upon domain model. Clients might agree about such ‘whys’ globally by agreeing on common semantics.

WebID: A URI for Every Agent

  • The WebID …/card#me names the agent; the document …/card describes it

Who May Do What? Web Access Control

Why may bidders append to the bids container, but not write to it?
  • Modes: Read, Write, Append (add, never remove) and Control (change the rules)
  • acl:accessTo is the container itself, acl:default is inherited by everything in it
  • acl:agent names one WebID; acl:agentClass foaf:Agent is anyone
  • The pod enforces the sealed bid, not your code
# /pitas-g3/pitas/auctions/a-001/bids/.acl
@prefix acl:  <http://www.w3.org/ns/auth/acl#> .
@prefix foaf: <http://xmlns.com/foaf/0.1/> .

<#submit> a acl:Authorization ;
    acl:agentClass foaf:Agent ;
    acl:accessTo   <./> ;
    acl:default    <./> ;
    acl:mode       acl:Append .

<#house> a acl:Authorization ;
    acl:agent    </pitas-g3/profile/card#me> ;
    acl:accessTo <./> ;
    acl:default  <./> ;
    acl:mode     acl:Read, acl:Write, acl:Control .

Data Sovereignty: Who Owns What?

Whose pod does a bid belong in?
  • The sovereignty principle of Assignment 9: data stays in the pod of the entity that generates it, and only that entity decides who may use it
  • Others refer to it by its URI and keep no authoritative copies
  • Hard cases:
    • the auction is the house's record, but the task is the client's
    • a bid is the bidder's, but it is evidence for the house
    • a result is the worker's, but the client paid for it

Critical View: Where Does Solid Hurt?

Which non-functional properties does Solid improve, and which does it cost?
  • Performance: following links means many small requests, across servers
  • Consistency: no transactions across resources and pods; partial failure is normal
  • Power: whoever hosts pods and identity providers gains a new central position
  • Usability: people must understand the access rules they set
  • Agreement: apps interoperate only if they share vocabularies and shapes

Data Decentralization: Limits of Personal Data Storage

A lot of the interesting data about a subject…

…needs to be asserted by an authoritative source (e.g., a bank, a doctor, a state agency)

…is about what the subject did using a service (e.g., buying, searching) and is generated and owned by the services

…was given by others about the subject and the content it produced (e.g., ratings, reviews)

No convincing business model (yet?) for personal data storage. Today’s BMs depend on exclusive data control

Services could still ask for «all data» and cut users if this is revoked. If users lack alternatives, they will consent to this!

The lack of alternatives (i.e., of interoperability) and the issues with consent are beyond personal data storage.

If we want to tackle them, we might need to regulate for openness. Some argue that this is already there, but that it today lacks teeth.

Zihlmann, Garcia, Mayer, Tamò-Larrieux: A right to repair privacy-invasive services: Is a new, more holistic European approach emerging? International Conference on Privacy-Friendly and Trustworthy Technology for Society, 2022
