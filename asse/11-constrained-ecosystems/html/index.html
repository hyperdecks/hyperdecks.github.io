Model Context Protocol: Overview

Providers expose functions through «tools» that are defined as

-Tool Name

-Tool Description in natural language

-JSON Schema for in- and outputs

MCP Resources != REST Resources; more like dynamic data sources to feed into LLM context (today read-only)

Providers may expose parameterized templates that help LLMs generate requests to the tool: server-side prompt libraries

Communication happens through a channel that is seen as persistent and bi-directional (i.e., a session)

-Like stdio… where does this come from?

-MCP hence has a session model (lifecycle, cancellations, heartbeat, streaming…)

-Optimized for long-lived agent/tool interaction

Build an MCP server - Model Context Protocol

Any downsides?

Exploit Asymmetries: Radio Duty Cycling

Radio Duty Cycling: Listen in without being switched on!

-Low-power Listening (LPL): Receiver periodically turns on radio and polls medium

-Low-power Probing (LPP): Reverses LPL roles – Receivers periodically send probes; Sender listens for probes and sends payload immediately after receiving a probe

More explanation: https://github.com/contiki-os/contiki/wiki/Radio-duty-cycling

Practical LPL protocols (e.g., Contiki X-MAC) can reduce the duty cycle to under 5%

e.g., wake up for 50μs every 1000μs

Challenge: Fast shutdowns and wake-ups

6LoWPAN: Standardized IPv6 over LoWPAN

Standard end-to-end Internet integration of resource-constrained devices

-Use IP as a narrow waist, also for resource-constrained devices

-Simple transformation between compressed and uncompressed formats

-Transformation is standardized to guarantee interoperability

BLE-6LoWPAN (RFC 7668)

BLE (full stack)

6LoWPAN provides specifications for transporting IPv6 packets over BLE (RFC 7668) and over IEEE 802.15.4 (RFC 4944) while recognizing and implementing LoWPAN constraints.

This is your go-to for global integration of constrained devices!

The Hypertext Transfer Protocol (HTTP/X)

HTTP is today not anymore text-based (luckily…)

With HTTP/3 (“HTTP-over-QUIC”) we’ve managed to separate it from TCP…

While HTTP’s uniform interface is very much desired for constrained devices (interoperability…), it is still a protocol made for plugged-in devices, and not well-suited for resource-constrained devices

Examples

-QUIC mandates encryption (TLS 1.3)

-QUIC packet reordering/congestion control

The Constrained Application Protocol

Efficient REST Uniform Interface on top of UDP

Lightweight security to prevent eavesdropping, tampering, forgery

Great for M2M applications: Multicast & Observe!

CoAP targets constrained nodes with limited memory and processing power

CoAP targets constrained networks that can be slow, unreliable, and intermittent (bad for TCP and QUIC)

Examples of CoAP Optimizations

-Goodbye streams! CoAP is based on pure UDP, avoiding the three-way handshake and connection management overhead

-Reliability of CoAP can be customized

-Smaller, more constrained headers

-Motivation to use small payload formats such as application/cbor (Constrained Binary Object Representation)

 IETF RFC 7252
